#+TITLE: RFC 0001 — Staging.org Metadata Format & Decision Drawer
#+DATE: [2026-07-08 Tue]
#+STATUS: Discussion

* Problem
  After Plaud audio recordings are downloaded to ~/Downloads, there is no
  structured way for the user to decide which recordings should enter the
  digital assets system. The current scan-and-stage-downloads function
  writes minimal metadata (:HASH: and :SOURCE: only), providing no
  information about the recording's content or date. The user has to open
  each MP3 file to decide whether to ingest it.

* Proposal
  Extend scan-and-stage-downloads with technical metadata from the filename
  and ffprobe, and introduce a formal :DECISION: drawer in staging.org for
  the user to confirm actions.

** Metadata Properties

  | Property     | Source                  | Purpose                                  |
  |--------------+-------------------------+------------------------------------------|
  | :HASH:       | SHA-256 of file         | Content identity                         |
  | :PLAUD-ID:   | .plaud-mapping.json     | Link to Plaud API record (future slice)  |
  | :CREATED:    | Regex from filename     | Recording date (YYYY-MM-DD)              |
  | :DURATION:   | ffprobe                 | Length (MM:SS)                           |
  | :BITRATE:    | ffprobe                 | Audio quality (e.g. 128k)               |
  | :SOURCE:     | Filesystem path         | Original location in Downloads           |
  | :SYNOPSIS:   | Empty, user fills later | Human summary after listening            |
  | :CLEANUP:    | Empty, user fills       | Confirmation text for REJECT (see below) |
  | :KIND:       | Fixed string            | "Plaud-voice-record"                     |

** Decision Drawer

  A formal ~:DECISION:~ drawer (parallel to ~:PROPERTIES:~ and ~:LOGBOOK:~)
  contains three checkboxes:

  - [ ] INGEST  — move file to assets/objects/<UUID>/raw/
  - [ ] REJECT  — delete file from Downloads
  - [ ] IGNORE  — keep file in Downloads, remove from TODO

** Explicit Confirmation for Destructive Actions

  REJECT requires an explicit confirmation text in the ~:CLEANUP:~ property
  (e.g. "Yes, delete it"). This prevents accidental deletion. INGEST does
  not require confirmation text since it is non-destructive (file is moved,
  not deleted).

  If ~:CLEANUP:~ is empty or does not match the expected text, the worker
  will not delete the file.

** Staging.org Entry Template

#+BEGIN_SRC org
* TODO [12 min] 2026-07-07 16_53_06.mp3
  :PROPERTIES:
  :HASH:       a1b2c3d4e5f6...
  :PLAUD-ID:   
  :CREATED:    2026-07-07
  :DURATION:   04:45
  :BITRATE:    128k
  :SOURCE:     ~/Downloads/2026-07-07 16_53_06.mp3
  :SYNOPSIS:   
  :CLEANUP:
  :KIND:       Plaud-voice-record
  :END:
  :DECISION:
  - [ ] INGEST  (Move to assets/objects/UUID/)
  - [ ] REJECT  (Delete from Downloads)
  - [ ] IGNORE  (Keep in Downloads, remove from TODO)
  :END:
  :LOGBOOK:
  - [2026-07-08 Tue 15:30] Auto-detected by Staging Worker.
  :END:
#+END_SRC

* Alternatives Considered

** ~:CONFIRMED: yes~ property instead of checkbox decisions
   Simpler but less expressive. A single confirmation property cannot
   distinguish between INGEST, REJECT, and IGNORE actions.

** ID3 tag embedding
   Writing plaud-id and metadata directly into MP3 ID3v2 tags was initially
   considered and set aside. Upon further discussion, the decision is:

   *Deferred, not rejected.* ID3 tagging has strong advantages that will be
   evaluated after the core ingestion pipeline stabilizes (Slices 1–3).

   Advantages over ~.plaud-mapping.json~:

   - **Same toolchain:** ffprobe is already invoked for duration and bitrate
     extraction. Reading plaud-id from an ID3 tag is just a different
     ~-show_entries~ flag — no new file format, no JSON parsing. Compared
     to ~.plaud-mapping.json~, ID3 eliminates an external dependency.

   - **Per-file metadata travels with the file:** If the MP3 is shared,
     moved, or archived, the plaud-id stays embedded. A ~.json~ mapping
     file can be lost or drift out of sync.

   - **Self-identifying downloads:** When plaud-downloader writes plaud-id
     into ID3 at download time, automatically downloaded files are
     self-identifying. Manually downloaded files (no ID3 tag) will have an
     empty ~:PLAUD-ID:~ property in staging.org, clearly marking them for
     human matching via ~:PREVIEW:~ transcription.

   - **Archival resilience:** In 10–20 years, the MP3 will still be
     readable. The ~.plaud-mapping.json~ file may not exist.

   Concerns and mitigation:

   - *SHA-256 mutation:* Hash identity is computed before tagging (on raw
     bytes). After INGEST, the file lives in ~assets/objects/<UUID>/raw/~
     where UUID is the canonical identity — hash mutation is irrelevant.

   - *Two file versions:* Applies only if tagging happens pre-ingest on
     the Downloads original. Post-ingest tagging (on the archived copy)
     creates no duplication.

   - *Same-timestamp collisions:* Two recordings can share a timestamp. A
     manually downloaded file without ID3 cannot be auto-matched. This
     is a human triage problem that ~:PREVIEW:~ transcription addresses —
     not a weakness of ID3 specifically.

** Plaud-ID in Properties
   :PLAUD-ID: is included as an empty placeholder. For the first slice,
   this property remains empty. Future slices will populate it from one
   of two sources (to be evaluated):

   - ID3 tag embedded by plaud-downloader (preferred — self-contained,
     same ffprobe toolchain)
   - ~.plaud-mapping.json~ mapping maintained by plaud-downloader
     (compatible with non-tagged files)

* Open Questions → Resolved (2026-07-08)

  **1. Should the worker append a new :LOGBOOK: entry for each action?**
  *Answer: Yes.*

  *Rationale:* Every worker action (INGEST, REJECT, IGNORE) must be recorded
  in the ~:LOGBOOK:~ drawer for full traceability and transparency. The
  staging.org file serves as both a decision panel and an audit log. Example:

  :LOGBOOK:
  - [2026-07-08 Tue 15:30] Auto-detected by Staging Worker.
  - [2026-07-08 Tue 16:00] Decision: INGEST. Moved to assets/objects/ab/cd/<UUID>/raw/
  :END:

  **2. DURATION format: MM:SS or "Xm Xs"?**
  *Answer: MM:SS (e.g. ~04:45~).*

  *Rationale:* FFmpeg/ffprobe uses this format natively (~-show_entries
  format=duration~ outputs seconds as a float). Converting to ~H:MM:SS~ or
  ~MM:SS~ is a standard transformation. The template in
  ~/org/h0_runway/org-staging.org~ also uses ~[00:00]~. Consistency with
  ffmpeg tooling avoids unnecessary format conversions.

  **3. Should the TODO headline include duration (e.g. "[12 min]")?**
  *Answer: Yes.*

  *Rationale:* The headline is always visible — even when the
  ~:PROPERTIES:~ and ~:DECISION:~ drawers are folded. Duration is the most
  important signal for triage: a 2-minute note vs. a 2-hour meeting. Seeing
  it immediately at the headline level lets the user decide without
  expanding every entry. Format: whole minutes, rounded up (ffprobe
  seconds → ceiling to minutes). Example: ~* TODO [12 min] 2026-07-07
  16_53_06.mp3~
